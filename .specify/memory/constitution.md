# Card Platform Constitution

## Core Principles

### I. 保留现有架构与工作成果
沿用 Next.js + TypeScript、FastAPI + Python 和 PostgreSQL 的现有职责边界。增量修改，保留用户未提交工作，不为采用开发工具重写业务。

### II. 识别结论可追溯
保留原始图片、处理结果与字段证据。区分视觉提取、联网核验和人工确认；未知或冲突字段明确呈现，不用无证据的猜测冒充确定结果。保留现有人工校正能力。

### III. 修复必须验证原始症状
识别缺陷记录可访问的失败样本、预期结果和实际结果，定位故障环节，再进行最小修复。使用针对性的测试及可用的真实样本回放，覆盖相关正常对照；未验证的部分如实说明。

### IV. 账户与数据隔离
保持现有登录鉴权、账户所有权和私有图片访问边界。不得将密钥、明文环境配置或账户隐私写入规格与报告。修改识别逻辑不得顺带覆盖真实卡库或估值数据。

### V. 估值和识别依据真实证据
保留真实市场证据、来源和不确定性表达。识别信息不足不伪造身份；成交证据不足不伪造市场价格，不以采购成本替代市场估值。

## Development Workflow

复杂功能用一份规格、技术计划和任务清单驱动开发；缺陷使用精简的评估、修复、验证记录。Spec Kit 负责持久化这些记录，Superpowers 可在其基础上执行工程流程。小改动按需验证，避免重复规划。详见 `docs/ai-development-workflow.md`。

## Governance

这些约定根据 README.md 的现有架构和行为约束，以及本次工具接入目标整理。后续明确的用户要求优先；有实际需求变化时同步相关规格。完成报告给出真实验证结果及局限，不以安装工具代替质量证明。
