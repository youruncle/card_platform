# 背面扫描长时间无响应

日期：2026-10-14。来源：用户刚完成的一次录入。判定：有效，严重度 high。

现场：最新会话背面为八张。数据库连接 6217 在区域 INSERT 后 idle in transaction 超过七分钟；配对连接 8805 在会话 FOR UPDATE 等待该连接，超过四分钟。日志有取图进度轮询和 Apple Vision orientation unavailable。进程清单有二十余个 Swift 方向判断进程持续存活数分钟。

根因：每个区域方向识别与 OCR 串行各等待最多20秒；超时返回降级值但不杀死或回收进程。整版处理从开始到结束持有会话行锁；配对因此阻塞。采样显示方向判断进程等待 AppleNeuralEngine 模型加载的同步 XPC 返回。尝试 CPU-only 的临时脚本仍超过15秒，不能据此宣称底层系统已恢复。

失败测试：orientation timeout/cancel、crop OCR timeout 均留下存活子进程；串行限编补读和门控忽略 OCR 测试失败。

修复方向：有限并发、超时/取消彻底回收进程、同版失败降级、在耗时处理完成后取数据库行锁、前端持续显示裁图进度。保留原图与识别不确定性，不修改真实卡库。


## 第二阶段诊断：完整八张录入与本机超时

09:35批次八张卡片平均排队134.997秒、处理163.954秒，整批433.292秒。旧worker在网络/OCR等待期间持有连接和事务；SQL now()是事务开始时间，造成finished_at与started_at仅差1–30毫秒。旧阶段使用归一化图片和最终图片mtime估算，不把错误的完成时间戳作为性能证据。

本机10 CPU、16 GiB。ANECompilerService采样时约90–99%单核CPU；进程已存在约9.5小时，不等于持续编译9.5小时。历史swap约13.5GB，但memory_pressure显示约49%可用，不能仅据swap断定当前内存不足。API进程样本同时显示cv2 JPEG解码/复制在事件循环线程运行，这是确定的应用阻塞。

对同一张真实背面图，准确OCR默认设备和显式CPU均15秒超时；旧算法版本、英文单语言也12秒超时。CPU探针已输出VNComputeStageMain选择CPU，但调用栈仍进入Espresso/AOT编译、分段路径和ANE校验。轻量fast OCR在1.159秒返回，倒向图片文字质量差，不作为准确OCR替代。证据支持准确识别模型初始化/编译异常或过慢，尚未确认操作系统内部根因，也不能断言机器配置不足。未终止root系统服务或重启电脑。

诊断临时探针与进程样本保存在.runtime/recognition-concurrency与/tmp；应用修复采用熔断降级，不能称为底层准确OCR恢复。
