# 卡淘短信发送流程缺失

## 问题与证据

用户在账号验证页面收不到短信。旧代码仅识别登录响应中的 needVerify=1，立即显示短信输入框，没有调用短信发送接口。
2026-10-04 只读检查官网 https://cardhobby.com.cn/Verify：官网先嵌入 cms.cardhobby.com.cn/checkcode/index，收到滑块完成消息后才 POST /Verify/SendSMS/，status=1 表示官网确认发送成功。验证码组件页面未返回阻止嵌入的 X-Frame-Options/CSP。

## 修复范围与实现

- 保留人工滑块；嵌入官网组件，不生成、模拟或绕过滑块答案。
- 只有当前 iframe 的精确来源和窗口发出的 checkcode 消息才触发发送。
- 后台从当前用户加密挑战中取得手机号与会话，沿用官网发送参数；不接受前端指定其他接收人。
- 只有官网明确确认成功才记录 sms_sent 并启用验证码提交。页面刷新可恢复发送状态。
- 发送失败或网络结果不明不显示成功；POST 不自动重试，所有尝试限制 60 秒间隔。
- 保留现有账号替换、移除和加密保存逻辑，不修改任何购买成本。

- 新增测试先失败：旧服务没有发送能力，旧前端没有滑块发送组件。

- 独立临时 PostgreSQL 中账号及短信相关测试：53 passed。包含真实路由鉴权、账号隔离、状态持久化和冷却；一条既有 Starlette 弃用警告。
- Next.js 生产构建与类型检查通过；本地 API/Web 已重新部署。
- 真实官网页面只读核查；未自动操作滑块，未使用真实账户发送短信或验证手机收件。
- 未运行全仓库测试。桌面浏览器工具初始化超时，未完成浏览器实点验收；组件通过 DOM 交互测试。

## 后续修复：过期挑战恢复

用户 20:40 截图已经加载新版本，但旧挑战过期后 GET verification 始终返回 LOGIN_REQUIRED，界面只能反复读取状态。改为明确 VERIFICATION_EXPIRED，并提供 POST restart-verification：用当前用户保留的加密凭据重新登录，不复用过期令牌/Cookie，不要求重复输入密码。凭据丢失或被拒绝时才回到登录表单；保留冷却、账号隔离和人工滑块。

回归先复现旧前端缺少恢复按钮、旧后端无法恢复；修复后前端相关测试 69 passed，独立临时 PostgreSQL 下后端相关测试 54 passed，生产构建和类型检查通过。真实卡淘登录及短信送达仍未实测。
