# 卡淘购买订单与库存购入成本

## 主动点击获取成本时强制刷新（2026-09-20）

- 单卡“获取成本”每次重新生成查询词、校验卡淘登录态并搜索，不再因已有买入记录（包括 ¥0）跳过。
- 前端解析/确认请求显式发送 `refresh:true`；未显式刷新的旧接口和后台补录任务仍保留不覆盖保护。
- 唯一可靠同款更新原有单件买入交易的金额、分摊运费、币种、汇率和订单来源，不新增第二笔买入；同一库存卡自身占用的订单可参与刷新，其他卡占用的订单仍不能抢占。
- 多件同款需选单；查询失败、截断、未匹配、金额异常时原成本不变。有多笔买入或买入数量非一时仍会查询，但不猜测更新哪一笔账本。
- 迁移 `0071_cardhobby_cost_refresh_history.sql` 保存刷新前完整交易/来源与刷新后证据；成本审计接口返回 `refresh_history`。本机迁移管理员执行后需向应用角色授予新表 SELECT/INSERT 权限。
- 列表优先显示本次成功刷新的金额，不会被刷新前的缓存旧价（尤其 ¥0）盖住。批量自动补齐未录入成本的范围不变。
- 验证：71 项前端测试、146 项成本领域/查询测试通过；完整 pytest 1747 passed/43 skipped，含隔离 PostgreSQL 的完整套件 1789 passed/1 skipped；Ruff、typecheck/build、健康检查通过。Chrome 实点 ID 523（已有 ¥0），已发起后台搜索并进入未绑定账号的登录流程，不再因旧成本跳过；真实价格更新待账号登录。

## 产品内账号登录（2026-09-20，当前默认流程）

以下流程替代历史版本的 Chrome 扩展登录依赖，原扩展保留作兼容工具。

1. 应用新增迁移 `0070_cardhobby_account.sql`。点击“获取成本”后，后台按当前产品登录用户检查绑定账号。
2. 未绑定时自动展示账号密码表单；验证卡淘登录成功后，才永久保存加密凭据，并继续原卡片的查询。
3. 已绑定时先访问订单页核实会话；失效后用保存的账号密码自动续登。有效会话不会重复提交密码。
4. 密码错误暂停自动续登，提示重新绑定；短信验证需用户输入验证码，成功后继续。验证码挑战临时数据也加密，五分钟后不再接受，最多三次失败；失败重试间隔一分钟。不绕过卡淘验证码、风控或访问限制。
5. 在成本窗口“管理卡淘登录账号”中可替换或移除绑定。移除只删除此用户的凭据、会话和验证码挑战，不删除成本或订单证据。
6. 搜索读取购买订单和详情，只保留金额、商品身份、图片与来源链接，不保存收货地址、手机号、网页全文。既有金额校验、身份匹配、多笔确认、零成本保护保持不变。

### 安全与部署

- `cardhobby_account` 以 `owner_id` 为主键，所有接口依赖产品登录态，不接受调用方指定另一用户。
- 用户名密码、cookie、验证码挑战分别使用 Fernet 认证加密，密文同时绑定用户和用途；API 不回传密码或 cookie，也不把密码放进校验错误、URL、浏览器存储或应用日志。
- 默认后端密钥位于项目 `.runtime/secrets/cardhobby-account.key`（权限 600，目录 700，已被 Git 忽略）；可用 `CARDHOBBY_ACCOUNT_KEY_FILE` 指定私有持久卷路径。**备份数据库时须分开安全备份密钥；不要删除/重建密钥或提交版本库。**丢失密钥后需重新绑定，不能从数据库单独恢复密码。
- 同一产品用户的绑定、续登、订单查询通过数据库事务锁串行化，防止并发重复登录；未知页面结构和跨站跳转停止读取，不当成“零订单”。
- 登录/搜索响应 `Cache-Control: no-store`；外部部署必须启用 HTTPS，当前本机使用回环地址。前端代理超时 180 秒，后台单次查询上限 150 秒、10 页/100 单；达到范围限制返回不完整证据，不强行写成本。
- 这是对卡淘公开网站登录/订单页面的适配，不是官方开发者 API。页面或风控变化可能需要维护。自动化测试使用虚构账号和订单；真实账户登录成功及订单成本写入仍需首次在产品表单中完成验收。

## 使用（2026-09-08 更新）

1. 数据库依次应用 `0068_cardhobby_purchase_cost.sql`、`0069_cardhobby_live_cost_search.sql`。
2. Chrome 一次性安装 / 更新 `apps/cardhobby-importer` 连接扩展（版本 0.3.0），刷新卡库。
   也可从成本窗口下载 `/cardhobby-connector.zip`，解压后在 Chrome 扩展程序页加载。
3. 在同一 Chrome 打开并登录 `https://cardhobby.com.cn/Order/MyOrders`。
4. 卡库列表“买入价 / 购入总成本”栏直接点击“获取成本”：在该行成本栏显示“成本获取中”，
   自动按名称 / 知识库别名搜索订单，读取全单商品及详情实付，核对并分摊运费。
   唯一且证据充分时直接更新该行卡价与总成本，并在后台刷新当前页；不弹出等待窗口。
   无需填写关键词、选择搜索方式或再点确认。只有识别出多件同款购买记录时，
   该行提供“选择对应订单”，点击后才打开确认窗口，复用已有结果，不重新搜索。
   未找到、搜索中断或无法识别的记录在该行显示结果；未连接时提供“连接卡淘”。
   连续获取多张卡会自动排队，翻页不取消搜索；退出账号或离开卡库页面会取消未完成请求。
5. 勾选列表中的卡片后，点击表格上方“批量录入卡淘成本价”，仅把所选卡片加入后台队列。
   各行显示“成本获取中”，完成后直接更新金额；已有成本（包括零成本）、正在获取或待选订单的卡片会保留当前状态。
   开始后取消勾选、筛选或翻页不会改变已提交的卡片范围；没有可获取的选中卡片时按钮置灰。
6. 侧栏成本入口可设置成功录入目标，逐卡搜索。关闭窗口暂停任务，再打开可从断点继续。
7. 列表保留手工价格编辑；详情成本来源展示原始订单与分摊证据。

主流程不再导出 / 上传 JSON。旧导出器和 `/sync` API 保留为兼容工具。
搜索调用订单页实际 GET 接口 `/Order/MyOrders?status=0&searchTxt=...`，
清空卖家 / 订单号 / 标记限制，将日期设为 2000 年至当年年底。
每卡最多 3 个关键字、共 10 页 / 100 单，逐次请求，单请求 15 秒超时、总搜索 150 秒上限。
关键词由 `purchase_cost_search.py` 从卡牌信息自动提取：优先公开商品编号，
再使用标准球员名和中英文别名，避免三个查询都被同一语言的近义名字占满。
达到上限返回 `complete=false`，显示搜索未完成，不要求用户编写关键词，也不将未完整结果判为唯一同款。

Chrome 扩展只接受本机 3000 端口卡库页面的搜索消息，并在已登录的卡淘标签页发出同源 GET。
登录凭据不离开卡淘浏览器会话；回传的字段仍是私人购买记录，仅交给当前登录的本地卡库。
页面返回登录、读取错误或不完整结构时停止搜索，不能把它当成空结果。

### 登录过期排查（2026-09-20）

如果 API 的 `search-plan` 为 200，但没有 `search-result` 请求，失败可能发生在浏览器扩展读取订单时，而不是后端。
本次实测订单 GET 返回 302，跳转 `/Verify` 后返回登录页 200；原订单标签页仍显示旧订单，刷新后也进入登录页。
不要根据旧标签页内容认定登录仍有效，也不要将最终 HTTP 200 当作订单读取成功。

前端兼容现有 0.3.0 扩展的登录错误消息，单独显示“卡淘登录已过期”和“重新登录卡淘”链接。
用户在同一 Chrome 登录后点击“获取成本”重试；无需重装扩展。批量面板同样区分登录与扩展连接问题。
所有失败原因直接显示在行内，不再仅放在悬浮提示中。已有成本（包括零）被跳过时也显示原因，不覆盖原金额。
未登录时不会提交空订单，不写入成本；凭据始终留在卡淘浏览器会话中。

## 架构与兼容语义

- `purchase_cost.py`：严格输入模型、金额校验、分摊、身份与匹配评分。
- `purchase_cost_search.py`：从已有卡牌信息生成查询关键词，无手工输入步骤。
- `purchase_cost_matching.py`：成本专用平行与标题判定，兼容本机旧版估值模块。
- `purchase_cost_service.py`：同步、候选、原子确认、审计、持久化批量任务。
- `purchase_cost_api.py`：登录保护 API。owner 从 `current_user` 注入，客户端不能指定另一个 owner。
- `cost-capture.js`：浏览器本地只读采集，顺序分页/详情请求、15 秒请求超时、页数上限、取消。
- `cost-search.js`：按关键字请求订单搜索、保留关键字分页、补全详情。
- `background.js` / `platform-bridge.js`：限定本机卡库来源与卡淘域名的 Chrome 消息桥。
- `use-purchase-cost-lookup.ts`：随登录会话管理单卡后台队列、去重、取消和逐行结果。
- `purchase-cost-panel.tsx`：已有重复订单结果的确认、连接说明、持久化批量搜索与审计 UI。

复用现有 `CardIdentityResolver`、产品冲突判定、已发布知识库球员别名和
`PortfolioRepository.add_transaction` / `calculate_position`。
旧 CardHobby 新卡导入数据保持原义；没有将旧 flat capture 直接迁移为可信成本，旧记录缺少完整订单边界。

迁移新增五张表：

| `cardhobby_purchase_order` | owner + 订单号唯一；当前字段证据、hash、版本、抓取时间、错误 |

## 金额规则

总成本 = 订单行单件卡价 + 该件分摊运费。
设订单总件数 N，运费 S 分；每件基础运费 `S // N` 分，剩余 `S % N` 分
分给按商品编号（字符串）、件序排序的前若干件。例如 0.10 元 / 3 件 = 0.04、0.03、0.03。
不会使用浮点做除法，也不会对每件分别四舍五入后留下差额。

必须提供完整订单行、已知运费、可接受订单状态以及订单总额或实付。
凡给出的总额/实付均须严格等于所有行 `unit_price * quantity` 之和加运费。
非零折扣、退款、额外费用在当前公式下不能识别为可用成本，自动跳过；不猜测分配。
打包商品保持一个订单行的商品件语义参与订单运费分摊，但不允许分配给单张库存卡。
本版不支持包内物理卡成本分配，自动跳过此类记录；现有手工编辑入口仍可独立使用。

## 匹配与任务

召回使用知识库姓名/别名、来源商品链接、同源图片 URL；使用通用身份层，不按具体卡名写特例。
评分综合年份、品牌、产品/子产品、Insert、平行颜色、卡号、限编分子/总数、签字、球衣。
明确冲突直接排除；无法建立同款身份的记录自动跳过，不转成单候选人工确认。
图片 URL 相同只是来源信号；候选图片供人工核验。本版没有视觉嵌入/感知哈希匹配。

同款识别要求球员、年份、品牌、产品，以及已知 Insert／平行／限编／签字等身份信息一致。
库存未填写限编总数时，仍读取卡片定义的 `print_run`；已知 Patch 须有相应身份依据，
不能仅凭普通 Jersey 标题自动录入，明确的非 Patch 描述也不能被来源信号绕过。
普通 Base 不再强制订单标题包含卡号、来源图片或限编分子；明确的卡号或限编分子冲突仍会排除。
精确商品来源链接可以补足省略字段，但不能越过明确冲突。
系统先剔除不符合身份的搜索结果，再检查同款购买数量：一件自动录入，多件才需选择。
库存里存在另一张同款本身不产生人工确认；数据库占用约束仍保证同一订单件只能记给一张卡。
单条弱候选、金额问题或搜索不完整都只返回自动处理结果，不提供人工确认按钮。
即使用户已打开重复订单选择窗口，确认时也必须重新校验卡片身份和订单证据仍然有效。

任务按 `collection_item.created_at,id` 保存未有交易的卡片快照。UI 默认扫描上限为
`min(2000, max(100, X*20))`；服务端上限 2000。没找到/需人工确认不计入成功 X。
达到 X 则 completed；没有更多快照或达到上限则 exhausted；取消保留已成功项与扫描位置。
重试 cancelled/failed 从未处理的卡片继续；想重新扫描先前未命中的卡，可重新启动自动获取，或创建新任务。
任务结束后人工确认之前跳过的卡不会回写旧任务成功计数；旧任务保留当时结果。

新建 `browser_search` 任务由浏览器逐卡搜索并提交 `search-step`；每次提交重查登录身份、
任务归属、状态与卡片游标，重复提交返回原结果，取消后禁止新写入。
网络失败保留游标并标记 failed；恢复后从该卡继续。旧 `synced` 任务仍由后台 worker 处理。

worker 使用数据库行锁 `SKIP LOCKED`，每件一事务，并用每 owner advisory lock 协调同步/确认。
确认同时锁库存卡，重查候选 hash、订单状态、占用和既有交易。竞争同一订单件只能成功一次。
worker 进程中断事务回滚，队列状态仍可继续；单步骤异常最多自动重试 3 次后 failed。
日志只记 job ID/次数/固定错误类别，不记私人订单或 SQL 参数。任务 API 可查错误、进度及逐卡原因。
每次候选读取上限 10000 件，超过直接拒绝，避免截断后错误地认定唯一候选。
