# 025 — 录入正反面完整性

## 用户目标

用户要求恢复已错配的库存，再找出并实施代码和工程改进，落地新版本。保持现有Next.js、FastAPI、PostgreSQL和iPhone个人开发签名渠道。已有故障证据和数据恢复见`.specify/bugs/inventory-face-mismatch/`，不重新生成第二份故障结论。

## 范围与成功条件

1. 现有一组双图识别先独立观察两面，再判断关系；返回可追溯、绑定当前图片的consistent/conflict/unknown。移除先验“必为同一卡”。不新增两次单面付费模型调用。
2. 明确不同卡身份或重复正面不得自动创建库存、成本或估值任务。未知结果保留审核草稿，显示原因；用户明确查看当前双图后可确认未知，不能以普通配对确认绕过已知冲突。单面模式维持现有行为。
3. 年份/日期的差异不得独占OCR评分；纪念日期、赛季和版权区分处理，产品/insert等身份信号独立。OCR缺失不等于身份核验通过，同一OCR分数不得作为recognition再次加权。正确657批产品级配对胜过错误mirror_y。
4. 确认与提交绑定明确的源版面/版本/区域，在会话锁内检查。重新扫描或裁切后旧确认失效；晚到旧请求不得静默提交不同来源。开始下一批明确新会话；重扫当前批明确标识。背面处理中不再引导直接换下一批。
5. 门禁覆盖scanner自动入库、手机capture确认和网页从识别草稿入库。新增字段保持既有job状态枚举；旧客户端遇需要审核的数据返回可读错误，无法绕过。
6. 合法多主体设计不能仅因人名不同被拒绝；340 Generations和849 Impulse等设计有共同产品、编号/设计证据时可通过，否则保留未知。
7. 保留所有权隔离、历史源图、现有人工编辑、手工交易与已授权工作。低裁切质量和普通低识别置信度仍是提示，不能冒充明确错配。
8. 发布网页、所需API、本机扫描API和手机更新；个人iPhone覆盖安装，保留数据，读回版本并验证启动。生产`PURCHASE_COST_WORKER_ENABLED=true`，发布、回滚和健康检查均保持开启。

## 验收样本

- 657批：同球员异产品、纪念2024与赛季2023-24，不误选mirror_y；同款Instant之间无个体证据不宣称实体匹配通过。
- 806/809：正面OCR缺失的局部位置交换须明确未核验；有独立信号时正确交换。
- 846–853：不同批源图及识别结果中的不同球员/产品冲突不可入库；源版本发生变化后旧确认失败。
- 306/308/311/312：两次拍摄的重复正面被拦截或进入审核，不自动入库。
- 正常双面、合法多主体、缺一面、模型缺少新字段/解析失败、重复确认、旧客户端、图片替换后的过期审核。

## 发布与限制

实测结果记录样本数量和边界；模型未识别出的同款实体交换不能声称被解决。不引入新的全局“自动确认低可信身份”开关，不用成本推导市场价格。4张缺背面需要用户补扫，不生成虚构背面。
