# Feature Specification: 私人卡库 iPhone App

**Feature Branch**: 当前 codex/cardhobby-valuation-quality 分支增量工作，保留既有未提交修改
**Created**: 2026-10-05
**Status**: 第一阶段已获用户开工授权；实现与验证中，真机/HTTPS/模型接入待条件具备
**Input**: 为本人和少量朋友使用，采用已选择的 Capacitor 路线。用户确认继续使用之前的腾讯云服务器，卡库数据暂不上传，当前先做功能层面的打通。

## 当前阶段边界

- 目标服务器确定为现有腾讯云实例，不新购或迁移服务器。
- 不导出、上传或同步本地卡库、交易、图片及知识库内容；保留云端已有账户和数据，不清库。
- 首个里程碑为手机与云端联通：登录、空库展示、专用测试草稿与图片上传、任务状态恢复、人工确认测试入库、详情与私有图片读取、估值状态或明确的不可用提示、退出。
- 联调采用新建的隔离测试账户和合成样本；真实识别验证使用用户专门提供用于测试的照片，不从已有卡库取样上传。联调数据与真实收藏分离。
- 识别、估值服务未配置时验证明确的失败或未配置状态；不能以模拟结果宣称真实识别或估值已打通。
- 以下用户故事保留完整首版目标。朋友邀请、TestFlight 分发、20 组真实样本回归及多人容量验收为后续里程碑，不阻塞最初联通验证。

## User Scenarios & Testing

### User Story 1 - 手机上查看自己的卡库 (Priority: P1)

用户安装应用、登录，在手机上搜索卡片，查看正反面图片、成本、估值和成交证据。

**Why this priority**: 提供随身查阅卡库的核心价值。
**Independent Test**: 使用有测试卡片的账户完成登录、搜索、详情查看和退出。

**Acceptance Scenarios**:
1. 已有云端账户登录后可查看同一账户的云端卡库，网页版的修改在刷新后可见。
2. 无估值或证据不足时明确显示状态，不以采购成本代替估值。
3. 会话失效后引导重新登录；退出或切换账户后不显示前一账户的私有内容。

### User Story 2 - 拍摄正反面并确认入库 (Priority: P1)

用户拍摄或从相册选择卡片正反面，提交识别，检查字段和证据，校正后保存。

**Why this priority**: 利用手机相机完成日常录卡。
**Independent Test**: 以真实手机照片完成上传、后台识别、校正和入库闭环。

**Acceptance Scenarios**:
1. 选择照片后可预览、替换、旋转；取消权限时可返回且已有草稿不丢失。
2. 服务器确认接收任务后，切后台或重启应用仍能恢复任务进度和结果。
3. 上传尚未完成时中断，重开可从保留的草稿重试；不承诺锁屏继续上传。
4. 字段未知、冲突或识别失败时明确显示原因，允许人工编辑或重试。
5. 重复点击提交或保存不会生成重复任务或重复卡片。

### User Story 3 - 邀请少量朋友使用 (Priority: P2)

管理员可邀请朋友注册，撤销尚未使用的邀请；每个使用者有自己的登录凭证。

**Why this priority**: 支持小范围使用，同时维持账户边界。
**Independent Test**: 用两个普通测试账户与管理员验证邀请、登录和越权访问。

**Acceptance Scenarios**:
1. 无邀请、邀请过期或已使用时不能注册；既有账户无需重新注册。
2. 暂按独立卡库设计：其他账户不能读取、修改或删除本账户的卡片、照片、任务、交易和第三方绑定信息。
3. 管理员的邀请管理权限不自动授予浏览朋友私有卡库的权限。

### Edge Cases

- 网络中断、超时、重复提交、任务排队、模型额度耗尽和服务重启。
- 大尺寸照片、HEIC、横竖方向、强反光、正反面拍错或缺失。
- 会话过期、切换账户、设备丢失后的会话撤销。
- 模型成功但无可靠字段或成交证据；保留不确定性。
- 手机磁盘不足导致草稿无法保存时，明确告知而不显示已保存。

## Requirements

### Functional Requirements

- **FR-001**: 提供卡库、录卡、任务、我的四个主要入口，关键操作无需桌面鼠标。
- **FR-002**: 支持登录、退出、设备会话查看与撤销、受控邀请注册。
- **FR-003**: 搜索、详情、图片与估值证据遵循现有账户所有权和证据规则。
- **FR-004**: 支持拍照和相册正反面录入，保留原始上传证据及其处理结果。
- **FR-005**: 识别任务接收后持久保存，支持恢复查看、明确失败和可控重试。
- **FR-006**: 人工确认后才录入卡库；提交和保存具备防重复行为。
- **FR-007**: 手机与电脑使用同一云端账户的数据；本地 Mac 数据不自动迁移或双向同步。
- **FR-008**: 私有数据传输加密，照片不因知道地址即可访问；服务凭证不分发到手机。
- **FR-009**: 数据库、照片及恢复所需配置有服务器外备份，并验证可恢复。
- **FR-010**: 发布说明包含安装、更新、版本到期处理和问题反馈方式。

### Key Entities

- 账户与设备会话：账户所有权、设备登录状态和撤销状态。
- 邀请：创建者、使用状态、到期时间；不携带管理员权限。
- 录卡草稿：正反面照片、人工编辑字段、上传状态及所属账户。
- 识别任务：任务归属、处理状态、字段证据、失败信息与入库结果。
- 卡片、交易和估值：沿用既有业务实体及证据关系。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 本人及至少一位受邀朋友在各自真机上完成安装、登录、搜索与详情查看。
- **SC-002**: 至少 20 组真实正反面照片完成测试，覆盖普通卡、评级盒、反光和旋转照片；逐组记录结果，不要求模型全部准确，但不得静默丢失或伪造字段。
- **SC-003**: 对上传中断、任务提交后切后台、应用重启、重复保存各重复验证 3 次，无确认成功的数据丢失或重复入库。
- **SC-004**: 两个账户的卡片、图片、任务、交易及第三方绑定越权测试全部被拒绝。
- **SC-005**: 暂以 5 人同时查阅、2 人提交录卡验证低并发使用；正常网络下连续 20 次查阅中至少 19 次在 3 秒内展示列表或详情主要内容，图片与后台识别单独记录耗时。
- **SC-006**: 从服务器外备份恢复至隔离环境后，抽查账户归属、卡片数量、照片与交易一致。

## 2026-10-07 手机交互增量（用户已确认实施）

在已存在的 Capacitor 客户端上改造，沿用「卡库、录卡、任务、我的」。桌面扫描仪、目录监听和知识库发布管理不进入手机导航，网页版保持原有能力。数据迁移由独立任务负责，本次不操作真实云端数据。

本次可在本地完成的交互验收：
- 相机与相册为仅有的照片来源；浏览器手机预览也提供后置相机输入。
- 相册一次最多选择 20 张照片，按正背面顺序形成待编辑队列；可重新排序、交换正反面、替换、手动裁切及旋转。奇数照片保留为缺背面的草稿，不能伪造背面提交。
- 草稿队列按账户及服务器隔离；编辑、删除和上传完成均持久化；重开恢复未上传照片，上传重试复用请求ID。收到服务端任务后只移除对应草稿，仍有草稿时继续录卡。
- 处理图片时限制输出长边至 2560 像素，保持比例和旋转方向；不支持的图片格式给出可操作提示。处理的是手机上传副本，原相册文件不改动。
- 私有图片按需加载，可重试；在 App 内打开大图，提供缩放与关闭，不跳转新浏览器页面；证据折叠展示。
- 卡库支持已有服务端的持仓筛选；排序仅在已确认存在服务端全库排序能力后接入，禁止把单页排序伪称全库排序。

尚需独立贯通的首版项：真正单面识别（当前共享识别队列依赖正反两面）、知识库只读查询、缩略图服务、自动取景裁切。以上不能以界面隐藏或模拟识别冒充完成。HTTPS、完整 Xcode、签名、真机相机/HEIC/多点触控验证作为安装验收条件。

### 两端共享边界（2026-10-07 用户补充）

- 后端为业务规则唯一权威：识别、估值、知识库、账户所有权、任务幂等和入库校验不在手机重写。
- packages/card-core 保存纯 TypeScript 接口契约和卡牌身份转换；Web 和 Mobile 都直接引用，禁止从手机导入 Web 页面、网络凭证或组件。
- Web 的 Cookie / Next 代理与 Mobile 的 Bearer / 原生 HTTP / Keychain 为各自适配器；共享类型不能包含设备存储逻辑。
- 手机独立：相机/相册、照片处理、草稿队列、底部导航、触屏编辑。Web 独立：扫描仪、目录监听、桌面批量管理。
- 跨端改动必须运行共享行为测试以及两端类型检查/构建；发布打包必须包含共享源，不能只在本地能编译。
- 域名、Apple账号和真机安装由用户之后补充，先完成功能开发。

## 第二阶段设计：单面识别、自动取景裁切、全库排序、缩略图（2026-10-07）

**状态：第二阶段代码与本地隔离验证已完成；完整原生构建、真机及真实样本验收待完成。** 域名、Apple账号和签名以后提供。本节作为四项能力的唯一设计依据，覆盖前文“只能双面提交”的历史限制；实际验证结果以 verification.md 第二阶段记录为准。第一阶段记录继续保留。

### A. 目标与方案选择

目标是让同一账号在网页和手机得到一致的识别、排序、图片与权限结果。手机承担设备交互，服务端统一保存与处理，共享 TypeScript 定义接口和显示语义。

比较三种路线：

| 路线 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| 两端分别识别、排序、生成缩略图 | 各端开发自由 | 业务重复、结果漂移、存量数据兼容困难 | 不采用 |
| 全部在服务器，包括实时相机画面分析 | 算法集中 | 实时预览依赖网络且持续上传相机画面 | 不采用实时部分 |
| 手机本地取景提示 + 共享后端正式处理 | 取景响应快，最终结果和权限统一 | 需要薄原生相机适配器 | 推荐 |

建议首版交互：用户按快门，系统提出裁切建议，用户接受、调整或保留原图；不默认自动连拍。用户已批准按此方案实施。相册导入使用同一套拍后裁切服务。

### B. 已核对的实现约束

1. `mobile_api.py` 上传强制 front/back 两张；`scanner_queue.py` 保存、判向、识别、确认入库均访问两个图片路径；`ScannerRecognitionJob` 的两个 URL 均为非空字符串。只改表单不能实现单面。
2. `scanner_api.py` 旧列表按 owner 查询全部扫描任务，当前没有排除手机任务。单面引入后要同时设计旧客户端隔离，不能往旧响应塞空字符串冒充图片。
3. `image_rectification.py` 已有四角检测与透视矫正，低置信度返回原图；应复用并拆出公开检测/应用步骤，不另写第二套正式裁切算法。`_rectify_pair` 的正反面互助裁切不能直接用于单面。
4. 手机 `capture.ts` 目前在设备上转 JPEG/压缩/手动裁切；相册原文件未修改，但未裁切上传副本没有独立保存在草稿中。后续必须区分源照片与编辑配方，才能撤销裁切和追溯。
5. `repository.list_items` 在 SQL 取数后执行联合估值合成与持仓成本计算。按 SQL 原始价格排序，会与屏幕最终展示数值不一致。
6. `/uploads` 已执行账户所有权检查并使用 private/no-store。缩略图不能绕开此边界；列表当前仍读取完整图片，CSS缩小和延迟加载都不是缩略图服务。

### C. 单面识别

**用户流程**

- 录卡支持“只有正面”“只有背面”“正反两面”；通常先拍正面。用户可以明确选择“先用这一面识别”，不再必须补齐背面。
- 多选照片提供“每张一张卡（正面/背面）”与“每两张配一张卡”模式，不猜测用户意图。未配齐的一张可保留草稿或明确按单面提交。
- 结果标明“仅有正面/背面”，未知年份、卡号、限编或评级保留未知，字段不足时保持待完善状态。具备入库必填字段后才可人工确认；保留现有业务必填校验。
- 单面可识别不等于可可靠估值。估值复用现有证据门槛，不以补拍缺失侧为由虚构信息。
- 已入库卡片可“补拍另一面”，更新同一 collection_item_id；新识别结果作为差异建议，原人工确认字段须用户明确接受才覆盖，不能另建重复卡片。

**共享模型与接口方向**

- 新的通用 CaptureService 负责所有来源任务的图片验证、持久化、幂等、状态流转和入库；现有 scanner/mobile 路由作为兼容适配器调用它，不再各自维护业务规则。
- 统一输入 `CaptureImages = {front?: image, back?: image}`，至少有一面；每面有源图引用、内容哈希、处理版本和裁切配方。客户端不能提供任意服务器文件路径。
- 提议新增通用 `/v1/capture/jobs` 上传、查看和确认接口，Cookie/Bearer均走现有 current_user。旧 `/v1/mobile/jobs` 双面协议继续可用；新客户端采用通用协议。
- 通用返回 `images.front/back` 可为空，明确 `available_sides`、`source`、`require_confirmation`、`revision` 和处理状态；类型进入 packages/card-core。旧 ScannerRecognitionJob 响应不直接改成可空。
- 数据库增量放宽缺失侧的路径/内容类型字段，约束“至少一面有效”“该侧路径/内容类型一致缺失或存在”；桌面自动入库来源仍要求双面。默认值兼容旧任务，不伪造空白或复制正面充当背面。
- 旧 scanner/mobile 列表适配器只输出其能表达的双面任务；历史双面记录不消失。单面记录从新通用列表读取，旧详情访问单面任务给出明确升级提示，不发生500或伪造URL。
- Worker仅遍历存在的面，单面走现有单图识别服务、双面走已有双图服务；共用证据规范化、身份确认与估值入口。缺失面的读取/旋转请求返回404，不能临时生成替代图。
- 幂等摘要涵盖面别、源图哈希、裁切配方、目标卡片及操作类型；网络重试复用 key，内容变化用新 key；同 key 不同内容409。补拍采用 target_item_id 与 expected_revision 校验，权限以当前会话判断。
- 排队前已经确定图片版本；运行中补拍/修改生成新任务版本，不能把旧模型响应覆盖到新版本。确认事务检查版本并锁定目标记录。历史结果保留作证据。

**验收**：正面单图、背面单图、双图各走完识别与人工确认；空输入422；缺失面404；补拍不增加卡片数量；重复提交/确认不重复入库；旧双面客户端和桌面自动入库回归；跨账号无法读取任务或补拍。

### D. 自动取景与裁切

分为三个步骤，避免把“拍完自动裁切”当成“实时取景”交付：

1. **取景提示（手机独立）**：原生相机预览叠加候选四角和“靠近一点/保持稳定/多张卡请选择目标”等提示。相机帧只在设备处理，限频检测，不持续上传视频；退出、切后台或权限撤销时停止相机会话。实时结果只供提示。
2. **拍后提议（两端共享）**：上传未裁切的标准化副本，服务端检测候选四边形、校验四角及透视变换，返回提议和置信状态。相册和网页上传也可用同一能力。
3. **人工确认**：预览源图与裁切结果，可拖动四角、旋转、恢复原图、重拍。用户确认后冻结图像版本再进入识别。低置信、强反光、多卡或边界不完整时保留原图/要求手动调整，不直接舍弃边缘。

**平台与算法边界**

- iOS建议使用薄 Capacitor 原生桥接，AVFoundation管理相机、Vision提供矩形候选；这只是设备候选检测。正式裁切、证据保存和图片版本由共享后端处理。
- 现有 Camera.getPhoto 能完成拍摄，但当前项目没有预览帧/叠框实现。不要只加静态框就声称具备实时检测。安装的插件版本以本地锁文件为准，不为在线文档变化顺带升级。
- 不直接用通用“文档扫描”结果覆盖卡图：评级盒、标签、厚卡、异形卡、横卡的保留范围不同。提供“保留卡面 / 保留评级盒与标签”选择；无法可靠判断时保留完整图片供用户确认。
- 设备提议、服务端提议、人工调整统一成 `CropProposal`：源图哈希、方向校正后的宽高、四点坐标、裁切目标、置信度/原因、算法版本。坐标统一左上原点、0–1范围、顺时针TL/TR/BR/BL；iOS坐标与镜像/横竖屏转换留在适配器。服务端验证凸性、自交、越界、最小面积及源图版本。
- 后端从现有 image_rectification 提取 `detect → propose → apply` 可复用接口。已人工确认的裁切输入不得被队列再次自动裁切；原图、提议和最终处理图均可追溯。
- 草稿保存未裁切副本 + 编辑配方；每次编辑从源图重建，避免JPEG反复裁切旋转积累损伤。草稿同时记录来源（相机/相册）和转换信息；所谓源图是本次送入系统的未裁切副本，不冒充保留原始HEIC字节。
- 提议使用私有、限时媒体资源；首版建议未绑定草稿资源保留24小时后清理，已绑定任务资源按任务保留策略处理。客户端离线保留源副本可重新获取提议；缓存清理不得删除正式入库图像。

**降级**：原生实时能力未就绪时保留系统相机 + 拍后自动建议 + 手动四角裁切；界面如实区分，不把降级路径当成实时检测通过。无网络仍能拍照存草稿，联网后再请求正式裁切提议。

**验收**：覆盖裸卡、评级盒、横卡、反光、倾斜、缺角、多卡、旋转EXIF；至少20组具备人工标注的授权真实样本，逐组记录边界保留和调整情况。合成图只测坐标、版本与权限，不作为裁切准确率证明。真实相机耗电、延迟和后台释放在真机上验证，当前环境不能宣称通过。

### E. 全库排序

**交互与规则**

- 两端使用同一组排序选项：录入时间（默认最新）、球员名称、赛季、持仓成本、正式估值；支持升/降序。名称首版按服务端规范化名称排序，不承诺中文拼音。
- 顺序固定为：当前账户权限 → 全库搜索/持仓筛选 → 生成最终展示值 → 全量排序 → 分页。切换排序、搜索或筛选回第一页。
- 同值以 collection_item_id 作稳定二级键；缺失值无论升降序均放最后；真正的0保留为0，不当作缺失。已售卡成本沿用当前持仓口径，界面明确标签为“持仓成本”。
- 正式估值采用与列表展示相同的联合合成结果；待审核影子估值不混入“正式估值”排序。金额计算及比较沿用后端Decimal，不经JavaScript浮点数重新计算；金额按账号基准币种可比，无法取得同口径数值的卡片归入“不可比较/暂无值”，不跨币种直接比较数值。

**实现方向**

- 现有 `/v1/portfolio/items/page` 增加白名单 sort_by/order；共享模块定义排序枚举、标签和请求组装。不得拼接客户端SQL片段。
- 将 repository 的最终字段组装抽成一个 PortfolioProjection，列表/排序共用相同的估值、成本、缺失值规则。搜索返回的候选ID也必须进入该投影，不能先截取候选ID分页再排序。
- 首期针对私人小卡库，在服务端对完整候选集合形成一次轻量展示投影，完成排序后分页；不在每页重新计算全部估值，不另起AI估值任务，不静默截取前N条。性能不达标则优化/建立读模型后再发布，不能降级成单页排序。
- 新客户端第一页可请求快照，后续分页带不透明 snapshot_token，绑定 owner、搜索条件、排序及基准币种。建议TTL60秒，缓存轻量列表投影及完整ID顺序，页面显示结果更新时间；期间估值更新不打乱翻页，刷新建立新快照。
- 快照只在现有单进程API内作限额短缓存，无需新购Redis；每账号至多3份、全局内存上限可配置，淘汰/重启/过期返回明确失效结果，客户端回第一页刷新。将来多进程部署时改用共享存储，不依赖负载均衡恰好命中原进程。
- 每次快照分页仍校验账号权限和记录是否有效。卡片被删除/转移则失效快照，不继续暴露缓存内容；退出会话失效后不能访问快照。客户端编辑/新增/删除后主动清除旧快照。
- 旧客户端不传排序继续默认最新；分页响应新增可选元信息，不改变原字段类型。优化读模型是后续性能措施，必须复用同一投影计算，不能写出第二套估值公式。

**验收**：用超过3页的测试数据验证最小/最大值位于末页时仍排序正确；同值、空值、0、混币种、已售卡、合成估值与数据库原值相反的样本；网页/手机相同条件返回同一ID序列；稳定快照不漏不重，变化与过期按规则刷新。以100/1000/5000张隔离样本在接近2核4GB环境记录冷/热耗时和内存，目标1000张热缓存首屏API p95≤500ms、冷请求≤3秒；这是验收目标，尚未实测。

### F. 私有缩略图服务

**显示策略**

- 列表用长边320px缩略图，详情预览用长边960px图，用户点开高清时才加载当前原尺寸处理图。保持比例、不放大小图、不额外裁切，不因生成缩略图丢掉评级标签。首版JPEG兼容两端，后续再评估WebP。
- 媒体描述增加可选 `thumb_url / preview_url / original_url / revision / width / height`；原有 image_front_url/image_back_url 保留。新两端通过同一选择规则决定尺寸。缩略图失败显示重试，不自动下载几十张原图掩盖故障。

**后端与存储**

- 统一 ImageVariantService 生成衍生图，复用现有上传格式校验、方向处理与账户权限。任务预览与收藏图调用同一生成器，资源权限分别按任务/卡片所有者检查。
- 提议接口 `GET /v1/portfolio/items/{id}/images/{side}?variant=thumb|preview|original&revision=...`；任务图片用对应任务路由适配。variant只允许固定枚举，不开放任意尺寸、路径或外部URL。
- 缓存键包含资源身份、面别、当前源内容哈希、尺寸、编码器版本；磁盘存放在私有衍生图目录，不能通过公开静态目录绕过鉴权。路径由服务端生成，拒绝符号链接和越界路径。
- 每次请求先验证会话、所有权、未删除状态和当前图片版本，再读取缓存；命中缓存也不省略权限检查。请求旧revision返回明确失效/不存在结果，不能返回旧版旋转前照片。
- 新上传/旋转/换图后生成新版本的缩略图，保存成功后原子发布；原图写入是主操作，衍生失败不回滚原图，可重试。旧版本不再可访问，后台清理闲置衍生文件。删除/恢复卡片都重新检查权限和版本。
- 存量图按需懒生成，可另用限速后台补齐；初始生成并发1，合并同一键的并发请求，用临时文件+原子改名防止读半张图。超出等待预算返回503/Retry-After，两端以有限次数退避重试并允许手动重试，不能无限轮询。
- HTTP继续 `Cache-Control: private, no-store` 与 `Vary: Cookie, Authorization`。性能收益来自服务器衍生缓存和传输体积下降，客户端只保留当前会话的有限内存Blob，退出/切账号释放；不引入公共CDN缓存。
- 限制解码像素和生成任务内存，图片变换放在有并发上限的执行器，不阻塞异步事件循环。磁盘配额和定期清理只影响衍生图；不足时明确失败，不删除源图。

**验收**：鉴权前不生成图片；匿名/跨账号/已删除资源被拒绝；GET/HEAD及缓存状态都保持权限；换图/旋转后新旧revision验证；并发只生成一次且没有半文件；列表首次加载不请求原尺寸图；抽样30张图片记录总字节和耗时，与直接原图比较；缩略图变小不能牺牲全部可辨认性，不对未知图片承诺固定压缩率。

### G. 共享边界、顺序和发布兼容

| 位置 | 本阶段职责 |
| --- | --- |
| packages/card-core | CaptureImages/任务与裁切提议/媒体版本/排序契约，参数验证与标签，缺失面与图片尺寸选择规则；不含平台副作用 |
| FastAPI领域服务 | 实际权限、文件持久化、裁切应用、识别/入库、最终展示投影、排序与私有衍生图；业务规则唯一权威 |
| apps/mobile | 相机预览桥接、触控四角、源图+配方草稿、缺失面交互、设备会话 |
| apps/web | 上传与四角交互、排序控件、缩略图显示、现有扫描仪入口；不引用手机组件 |

推荐交付顺序：①共享契约与单/双面数据模型 → ②单面全链路与补拍 → ③后端裁切提议+两端确认 → ④私有缩略图 → ⑤全库排序 → ⑥iOS实时取景桥接与真机验证。阶段③可先提供相册和系统相机拍后裁切，不等待域名/签名；阶段⑥单独记录真实设备验收。

发布先部署兼容性数据库变更，暂停并排空/交接旧worker，再启用可识别新协议的worker和兼容服务端，最后发布Web和Mobile；确认旧worker已退出前不开放单面任务创建。增加只读能力声明（支持的capture协议、单面、裁切、variants、sorts），新App连接旧服务器时隐藏不支持能力并解释升级条件；不能靠捕获500猜测支持情况。原有双面接口和原图URL在过渡期保留。

共享契约变更至少执行两端类型/构建检查、共享行为测试、临时PostgreSQL接口回归和新旧客户端契约用例；单面、裁切、变换、缓存与排序都覆盖账户隔离。客户端类型与Python响应的契约快照纳入回归，避免只编译TS仍遗漏服务端空值变化。

回退优先关闭新能力、保留旧接口和新增数据。已有单面记录不能通过反向强制NOT NULL迁移回退；旧worker也不能接手新协议单面任务。应停止领取新任务、让支持新协议的worker处理/暂停存量任务，再回退界面，不能直接回滚二进制并丢失图片。

### H. 设计依据与验证边界

- 以上现状由当前工作区源码核对，未连接云端、未迁移或修改真实数据。
- 原生矩形检测参考 [Apple Vision DetectRectanglesRequest](https://developer.apple.com/documentation/vision/detectrectanglesrequest)，它提供矩形候选；卡片/评级盒目标选择和可靠性是本项目需验证的设计，不是框架承诺。
- 拍摄/相册能力参考 [Capacitor Camera 官方文档](https://capacitorjs.com/docs/apis/camera)；在线版本与安装版本可能不同，实现以锁定依赖和目标iOS SDK实测为准。
- 设计后已按用户授权完成代码与隔离测试，结果见 verification.md；仍没有完整原生构建、真机或真实算法准确率结果。自动快门/连拍、公共CDN、全库离线同步、重新训练检测模型不在本阶段范围。
