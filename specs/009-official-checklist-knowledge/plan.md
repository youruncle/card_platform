# 自动官方清单知识实施计划

Goal: 自动采集近20年官方篮球清单并发布可查询知识，回放持仓并暴露真实进度。
Spec: spec.md
Tech: FastAPI/Python/PostgreSQL/Next.js，复用现有knowledge表、不可变快照与授权。

## Constitution Check
保留工作区修改与现有接口；官方源按用户本次指令自动批准，仅机器检查结构与冲突；未知字段保持未知。仅追加知识，不写历史卡片和估值。修改范围在新导入模块、查询模块、现有运行时的窄接口。

## Architecture
1. 官方目录 discovery → 冻结source manifest（发行日期证据/未知状态）→ 原文件content-addressed缓存。
2. PDF/XLSX抽取结构行；每行存section、卡号、球员、team、来源页号/行号，卡种作用域明确；无法解析的片段保留并计数。
3. 生成现有knowledge manifest，自动approved，幂等apply并以现有snapshot发布，标明auto_official来源。
4. ScopedCardCatalog索引先按产品/年份/卡号筛选再核对球员，仅唯一一致字段补全；共同字段可回填，版本冲突保留。并入KnowledgeResolver.normalize_identity，估值入口及知识validate统一使用。
5. JSON运行账本原子写；API只读展示。发现未完成时coverage为null；失败计已处理不计成功。
6. 全部有效持仓只读回放，记录原/新身份、知识来源、知识查询与卡淘query plan；586及负样本必测。不自动发布未经视觉确认的新价格。

### 建设范围与顺序

1. 沿用当前篮球范围，以“年份/赛季 → 厂商 → 正式产品 → 基础卡/特卡/平行/签字物料 → 具体卡片”为目录。保留联盟、授权、发行年份与赛季的不同含义，不把厂商归档年份直接当赛季。
2. Topps、Panini 为两条主线，覆盖范围不因账户是否持有该产品而增减。历史 Upper Deck、Fleer、SkyBox 等按同一目录方法补齐；其他运动与影视角色产品不因当前持仓自动插队。
3. 默认从 2025–26 的正式已发布产品开始，向 2024–25、2023–24 逐年推进，历史目标沿用 1996–97 起点。2026–27 等新赛季正式资料进入独立增量队列；预览资料单列，不猜测完整清单。
4. 每年先建立完整的已发现产品清单，再逐产品完成图文知识包。一个产品缺图或来源受阻时记录缺口并继续其他产品；年度状态如实保留 partial，不因转入下一年而自动记为完成。
5. 首个流程样板选择 2025–26 Topps Chrome Updates Basketball，因为官方同一页面可定位清单、赔率、教育资料及卡面展示。样板之后按该年度正式目录展开其余 Topps 与 Panini 产品，而不是只做热门或已有持仓的产品。

### 每个产品同时交付的知识包

**文字层：** 产品全名、厂商/品牌、联盟/授权、赛季、真实发行日期及依据；基础卡、特卡、签字/物料、平行版本表、限编或赔率；具体卡号与球员/多人物；各版本适用范围与区别。只展开来源明确证明的组合，不建立全清单乘全部平行的无证据笛卡尔积。

**图片层：** 按产品内所有已发现子系列和版本安排采集，先有系列设计参考、平行差异示例，再持续覆盖具体卡片的正反面。每张图绑定来源、产品/赛季、卡号与球员或适用设计、正反面角色、核验状态；必要时补纹理、限编、签字或物料局部图。包装图不算卡片正反面覆盖，少数系列示例也不算全套逐卡图片覆盖。

**存储与追溯：** 保存可使用的原始图像资产、缩略图、局部图及其关系；记录原网页、原图 URL、获取时间、内容哈希、图像类型、配对依据和访问范围。官方示意、核实实卡、未核实候选分别管理，未知版本不强行定名。自有私有照片继续保持账户边界，不能自动变成公共参考图。

**向量层：** 为已经保存的图片与文字生成可重建索引。正面、背面分别生成图像向量，必要的局部图单独索引；文字知识生成文本向量，厂商/赛季/卡号等仍有结构化和关键词索引。每条向量绑定实体或媒体 ID、来源哈希、模态、编码器/模型版本、维度、预处理版本、知识版本和可见范围。不同模型的向量不直接比较；需要文字搜图片时，使用经过验证的同一跨模态空间或分别召回后融合。

### 检索方案与现有能力

现有 PostgreSQL 继续保存实体、关系和来源；图片沿用受控文件/对象存储，向量作为派生索引。优先评估 PostgreSQL + pgvector，保持元数据过滤、版本和访问范围在同一数据库体系。pgvector 支持精确与近似向量检索；先用精确检索建立小批基线，再依据实际规模和延迟评估 HNSW，不预先承诺效果或阈值。

现有 `public_image_index.py` 是 SQLite + SIFT/几何特征的公开成交图片候选索引，不是通用语义图文向量库。保留其职责，可评估复用几何核对能力；官方知识图库与未验证成交候选的身份、来源和发布状态分别记录。

查询流程：上传或输入 → 图像裁切/方向及 OCR → 结构化/关键词与向量分别召回 → 融合候选 → 按产品、赛季、卡号、文字与正反面图像证据重排 → 返回相似卡、版本差异、来源及知识版本。已确定字段用于过滤，未确认识别字段采用软约束或多候选，避免错误初识别排除正确卡。

图像向量先比较图像/图文模型在实卡上的表现，模型家族和版本由样板评测决定。相似度只用于候选排序，不直接确认同版本、同实卡、品相或价格。离线或独立任务生成向量；先测资源占用，不把大型编码器加载到当前在线 API 请求路径。原图未变且模型/预处理版本相同则复用向量；换模型并行重建，验证后切换索引版本，支持回滚。

技术依据：https://github.com/pgvector/pgvector 。首批使用固定版本 Google SigLIP 的同一图文空间、768 维归一化向量和可移植精确余弦索引，编码离线运行，不向当前生产 API 加载约 813 MB 模型。生产 pgvector 迁移、应用内融合检索及独立卡牌评测仍是后续任务，不以自匹配查询冒充准确率验收。

### 覆盖与完成口径

保持 `docs/knowledge-coverage-denominator.md` 中 manufacturer × product × season × facet 的五类文字口径，同时单独记录下列图像和检索指标：
- 文字覆盖：基础卡、平行、特卡、签字物料、具体卡片身份分别统计。
- 设计图片覆盖：已有对应参考图的子系列/版本数 ÷ 有直接证据的目标子系列/版本数；官方示意与核实实卡分列。
- 逐卡图片覆盖：正面、背面及完整配对各自覆盖的、来源明确的卡片身份数 ÷ 已确认清单身份数；缺一面不能计入配对覆盖。
- 向量覆盖：指定模型/预处理/知识版本下，已建有效向量的可索引图文资产数 ÷ 应索引且可用的图文资产数；不能据此宣称图像资料本身齐全。
- 检索效果：固定测试集的 Recall@K、同图/近重复隔离后的召回、相邻版本混淆、Top-K 延迟、内存/磁盘占用及空结果；图片缺失与检索失败分开报告。
- 年度母集发现未完成时覆盖率分母记 unknown；受阻、日期未知和预览分别列出。已有文字而缺图的产品保留 image_partial，不标图文全覆盖；进入下一年不改变此状态。

评测集按年度产品目录取样，不按持仓分布抽样。覆盖同球员不同产品/赛季、同版不同球员、同卡不同平行、文字相近卡号、裸卡/卡壳/反光/旋转、正反面混用和图库未收录的卡。查询图与图库同图或近重复图单列，不能用自匹配成绩代替识别泛化效果。持仓回放作为附加使用验证。
