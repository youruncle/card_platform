# Feature Specification: 球员每日卡价涨跌

**Feature Branch**: `codex/cardhobby-valuation-quality`（保留当前工作区）
**Created**: 2026-10-12
**Status**: Accepted for first version
**Input**: 每位球员选三种常见卡，比较每日近7天成交中位价与前一天，按涨跌幅排序。用户已授权先实现一版。

## User Scenarios & Testing

### User Story 1 - 查看球员涨跌榜 (Priority: P1)
用户查看自己卡库球员的每日价格趋势，以三张固定代表卡的等权涨跌反映市场热度。
**Independent Test**: 三张卡各自涨10%、0%、跌10%，球员涨跌为0%。
**Acceptance Scenarios**:
1. 三张卡两个窗口均至少3笔成交时，展示等权涨跌并按涨幅或跌幅排序。
2. 少于三种代表卡或任一窗口不足3笔时，显示数据不足，排在有结果的球员后，不填0%。
3. 展示报告日期、两个7日窗口、样本笔数、来源、最新成交及采集时间；无新成交仍能因窗口滚动产生变化。

### User Story 2 - 发现与固定代表卡 (Priority: P1)
从卡淘已售样本中按近90天有效成交笔数选前三种同款，按月固定。
**Independent Test**: 重复商品只计一次，PSA10与裸卡分组；次日新高频卡不替换当月篮子。
**Acceptance Scenarios**:
1. 球员中英文和已有别名检索，分页有预算，结果注明采样覆盖而非全市场。
2. 年份、系列、卡号/卡种、平行版本、限编、签字/物料及评级不同不能混用；多人、套装、未知身份不入价。
3. 复用已有公开成交样本；新标题按保守明确字段解析并使用现有身份校验；不确定记录保留为候选。
4. 月初重新选择代表卡，用同一篮子重算两个窗口，明确换篮子而不产生换卡假涨跌。

### User Story 3 - 每日更新与预览 (Priority: P2)
后台每天自动补采代表卡，用户可请求更新并查看失败/排队状态；演示模式清楚标注。
**Independent Test**: 同日重跑幂等；采集失败保留历史统计且不伪装为零成交；演示不写真实数据。
**Acceptance Scenarios**:
1. 北京时间每天07:00以后处理前一天，后台逐球员限速，失败延后重试。
2. 登录用户只能读取和刷新其活动卡库球员；市场采样不包含私有图片、成本或账户信息。
3. 第一版页面含涨幅、跌幅、球员搜索、代表卡明细和独立演示预览。

### Edge Cases
空卡库、全部无效成交、重复/冲突商品、未来成交、混币种、未知平行或评级、月切换、窗口边界、采集部分失败、并发更新、尚未迁移数据库。

## Requirements
- FR-001: 使用上海时区自然日，报告D的当前窗口[D-6日00:00,D+1日00:00)，前日窗口[D-7日00:00,D日00:00)。
- FR-002: 只统计卡淘人民币已售且有出价的结束拍卖/可核验成交；使用成交价，不含运费。
- FR-003: 涨跌=(当前中位价/前日中位价-1)*100，三卡等权；先计算后显示四舍五入，最小每窗口3笔。
- FR-004: 每月首次凑齐三种卡后用截至报告日的近90天去重有效成交固定篮子；不足三种时允许补齐但不生成涨跌；同笔商品不重复或归入不同卡。
- FR-005: 无数据、身份不确定、来源异常、采样不完整必须可见；不得以成本、挂牌价或估计价格补足。
- FR-006: 保持现有鉴权与账户隔离，不改写卡库、估值及原有市场证据。

## Key Entities
球员、独立成交样本、月度代表卡篮子、每日快照、采集状态。

## Assumptions
第一版默认跟踪当前用户活动篮球卡库球员；共享公开市场统计，读取按用户球员范围过滤。支持明确可解析标题及现有身份，无法准确分组的标题不参与。三个代表卡指三个精确同款含评级状态。采集覆盖有预算，不宣称全市场或球员真实竞技价值。

## Success Criteria
- SC-001: 示例0%等权结果、3笔下限、时区和月切换均经测试确认。
- SC-002: 用户能从排行榜展开三种卡查看两个窗口价格、笔数和原始来源。
- SC-003: 每日更新可重跑且不会增加重复成交或泄漏另一账户的球员范围。
- SC-004: 页面真实无数据与演示模式清晰区分，故障状态不覆盖有效历史结果。

## 2026-10-12 发布范围

用户明确要求重新部署前端、发布云端新版本，并确认苹果手机版只需自己的 iPhone 开发模式测试版。保留云端现有账户、卡库、图片及配置，不上传本地业务数据。原生客户端在「我的」增加球员卡价涨跌入口，复用相同接口、分组口径、排序和来源；通过现有 Bearer 会话读取，不复制网页 Cookie。共享类型及排序/身份展示函数放在 card-core；演示仍仅在网页显式启用。

验收包括 Web/Mobile 构建、增量迁移、云端健康及鉴权、备份与回退点、iOS 真正编译及已配对开发设备安装。原生云端连接需要可核验的 HTTPS 地址；若尚未具备，明确区别安装成功与联网成功，不修改 ATS 或放行任意 HTTP。
