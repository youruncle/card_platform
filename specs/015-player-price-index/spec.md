# Feature Specification: 球员每日卡价涨跌

**Feature Branch**: `codex/cardhobby-valuation-quality`（保留当前工作区）
**Created**: 2026-10-12
**Status**: Accepted for first version
**Input**: 每位球员选三种常见卡，比较每日近7天成交中位价与前一天，按涨跌幅排序。用户已授权先实现一版。

## User Scenarios & Testing

### User Story 1 - 查看球员涨跌榜 (Priority: P1)
用户查看自己卡库球员的每日价格趋势，以三张固定代表卡的等权涨跌反映市场热度。
**Independent Test**: 三张卡各自涨10%、0%、跌10%，球员涨跌为0%。
**Acceptance Scenarios**:
1. 三张卡两个窗口均至少3笔成交时，展示等权涨跌并按涨幅或跌幅排序。
2. 少于三种代表卡或任一窗口不足3笔时，显示数据不足，排在有结果的球员后，不填0%。
3. 展示报告日期、两个7日窗口、样本笔数、来源、最新成交及采集时间；无新成交仍能因窗口滚动产生变化。

### User Story 2 - 发现与固定代表卡 (Priority: P1)
从卡淘已售样本中按近90天有效成交笔数选前三种同款，按月固定。
**Independent Test**: 重复商品只计一次，PSA10与裸卡分组；次日新高频卡不替换当月篮子。
**Acceptance Scenarios**:
1. 球员中英文和已有别名检索，分页有预算，结果注明采样覆盖而非全市场。
2. 年份、系列、卡号/卡种、平行版本、限编、签字/物料及评级不同不能混用；多人、套装、未知身份不入价。
3. 复用已有公开成交样本；新标题按保守明确字段解析并使用现有身份校验；不确定记录保留为候选。
4. 月初重新选择代表卡，用同一篮子重算两个窗口，明确换篮子而不产生换卡假涨跌。

### User Story 3 - 每日更新与预览 (Priority: P2)
后台每天自动补采代表卡，用户可请求更新并查看失败/排队状态；演示模式清楚标注。
**Independent Test**: 同日重跑幂等；采集失败保留历史统计且不伪装为零成交；演示不写真实数据。
**Acceptance Scenarios**:
1. 北京时间每天07:00以后处理前一天，后台逐球员限速，失败延后重试。
2. 登录用户只能读取和刷新其活动卡库球员；市场采样不包含私有图片、成本或账户信息。
3. 第一版页面含涨幅、跌幅、球员搜索、代表卡明细和独立演示预览。

### Edge Cases
空卡库、全部无效成交、重复/冲突商品、未来成交、混币种、未知平行或评级、月切换、窗口边界、采集部分失败、并发更新、尚未迁移数据库。

## Requirements
- FR-001: 使用上海时区自然日，报告D的当前窗口[D-6日00:00,D+1日00:00)，前日窗口[D-7日00:00,D日00:00)。
- FR-002: 只统计卡淘人民币已售且有出价的结束拍卖/可核验成交；使用成交价，不含运费。
- FR-003: 涨跌=(当前中位价/前日中位价-1)*100，三卡等权；先计算后显示四舍五入，最小每窗口3笔。
- FR-004: 每月首次凑齐三种卡后用截至报告日的近90天去重有效成交固定篮子；不足三种时允许补齐但不生成涨跌；同笔商品不重复或归入不同卡。
- FR-005: 无数据、身份不确定、来源异常、采样不完整必须可见；不得以成本、挂牌价或估计价格补足。
- FR-006: 保持现有鉴权与账户隔离，不改写卡库、估值及原有市场证据。

## Key Entities
球员、独立成交样本、月度代表卡篮子、每日快照、采集状态。

## Assumptions
第一版默认跟踪当前用户活动篮球卡库球员；共享公开市场统计，读取按用户球员范围过滤。支持明确可解析标题及现有身份，无法准确分组的标题不参与。三个代表卡指三个精确同款含评级状态。采集覆盖有预算，不宣称全市场或球员真实竞技价值。

## Success Criteria
- SC-001: 示例0%等权结果、3笔下限、时区和月切换均经测试确认。
- SC-002: 用户能从排行榜展开三种卡查看两个窗口价格、笔数和原始来源。
- SC-003: 每日更新可重跑且不会增加重复成交或泄漏另一账户的球员范围。
- SC-004: 页面真实无数据与演示模式清晰区分，故障状态不覆盖有效历史结果。

## 2026-10-12 发布范围

用户明确要求重新部署前端、发布云端新版本，并确认苹果手机版只需自己的 iPhone 开发模式测试版。保留云端现有账户、卡库、图片及配置，不上传本地业务数据。原生客户端在「我的」增加球员卡价涨跌入口，复用相同接口、分组口径、排序和来源；通过现有 Bearer 会话读取，不复制网页 Cookie。共享类型及排序/身份展示函数放在 card-core；演示仍仅在网页显式启用。

验收包括 Web/Mobile 构建、增量迁移、云端健康及鉴权、备份与回退点、iOS 真正编译及已配对开发设备安装。原生云端连接需要可核验的 HTTPS 地址；若尚未具备，明确区别安装成功与联网成功，不修改 ATS 或放行任意 HTTP。


## 2026-10-17 行情可用性优化 v2（用户已授权实施）
目标：让已有真实成交独立于三卡指数展示，解释缺失原因，提高补采针对性。保留当前功能分支的其他未提交工作。
- FR-007：返回market行情档案：近90天独立有效成交总数、卡款数、最近成交、全部确认卡款的近期成交及趋势；卡款最多20种，标注截断，不受月篮子限制。
- FR-008：每卡近30日与此前30日中位价、笔数；两窗各至少3笔才有变化，标为样本趋势、不冒充可靠估值。1张卡也展示，三卡指数门槛不变。报告D当前窗[D-29,D+1)，前窗[D-59,D-29)，上海时区。
- FR-009：覆盖计数以独立商品为单位，冲突商品剔除；保存多卡、赛季、评级、卡款字段不足/歧义等未纳入原因汇总。部分采集失败不宣称完整日更，不覆盖旧指数。
- FR-010：未固定阶段用已有确认的活跃卡款生成至多3个精确补采词，与别名共享12页预算。初始篮子优先两个7日窗口可比的卡款，仅三卡均可比时固定；既有月篮子不变。
- FR-011：可只刷新本账户持仓单个球员，范围外404，UUID校验，全量刷新兼容。两端概览显示跟踪/有成交/有卡款趋势/有指数；展示缺失原因、更新状态和单球员刷新。
- FR-012：GET从已保存成交派生market，兼容旧快照；按请求报告日截止，不引入未来成交；旧指数及行情日期分别标注。
- FR-013：只读覆盖审计，不输出账户或密钥；统计独立成交、卡款、趋势、指数和异常/缺失分布。
验收：一两种卡也展示成交来源和30日价格；低样本不填0%；覆盖隔离、历史日、冲突、边界、旧数据与两端交互。
边界：不放宽身份校验、不加新源/模型、不承诺指数覆盖率；30日为首版明确口径，多日期市场稳定性待真实回放。线上审计/发布依赖服务器访问，本地不能代替线上。

## 2026-10-22 v3：真实行情可用（持续任务，用户已授权实现及双端发布）

用户目的：能够依据真实、可比较的成交判断球员卡价变化及活跃程度。页面上线、刷新成功、演示或测试通过均不构成业务完成；稀疏对象保留未知，不伪造涨跌。

云端基线（报告日2026-10-21，全体持仓篮球球员并集）：314对象、100有成交、451笔/244卡款、0可比卡款/0球员指数。库里1687条旧观察因新增两个null字段被误拒；卖家尾码XBW10污染卡号及补采词；采集无历史推进。完整只读证据在`.runtime/player-price-review-20261022/`，后续验证保存同口径捕获，不把本地知识库作为主库。

- FR-014：旧公开观察缺少新增可选字段时，仅在当前值等于该字段的无信息默认值时兼容；原始行哈希、成交ID/标题/价格/日期/运费/评级及非默认元数据变化仍须拒绝。不得整体关闭事实校验或改写原始捕获。
- FR-015：卖家尾部串码不能建立正式卡号；未知卡号可通过有来源的卡款目录、详情/图片进一步确认，无法确认保留候选。不同产品、插入、平行、评级、限编不得合并。绑定收据的正面独立字段证据可补充标题省略的特卡名称，但仍须命中当前产品/赛季/卡号/球员的官方卡款；明确的其他卡种、Base或多个独立卡种声明不得作为省略处理。名称包含关系与官方资料缓存淘汰不得改变此判断。审计旧派生行情，按可回退的修复版本重建受影响身份、篮子与快照；业务卡库、成本及估值不变。
  同一球员的大小写/变音符/已核验完整姓名别名不能因内部UUID不同而互相排除成交；只合并确定的同一公开主体，保留Jr/III及多人主体边界，查询别名不自动成为身份别名。账户范围按原持仓主体授权，不能因主体归一化泄漏其他账户持仓。
- FR-016：在限速和每轮预算内保存逐查询历史游标，失败不跳页；增量从最新页采集，历史持续向前推进直到90日边界或源尾；空查询和已完成查询不持续耗尽预算。查询改变不继承别的查询游标。明确历史完成范围及采集新鲜度。
- FR-017：优先补足可比卡款和活跃球员，同时为全部持仓球员保留公平调度。后台不得在一次长事务中无限采集；可中断恢复、幂等、部分失败可见。
- FR-018：页面首屏直接呈现可用的球员行情：同款变化、可比卡款数、成交活跃程度、比较时间段和证据可靠程度；三卡7日指数可作为独立指标，不能让它缺失遮挡已有可用趋势。两端口径、排序、来源和缺失解释一致。
- FR-019：球员层面变化须由明确可比较的固定同款计算，披露构成、权重及覆盖，不能以不同卡的平均价格变化代替。保留原始成交及真实币种/不含运费口径；跨来源时分列，不把挂牌价作为成交。
  不同商品号复用完全相同正反面照片、尚不能确定独立成交证据的整组记录保留原始捕获并退出可比统计，不任意挑一笔代表真实成交或用它们凑足最小样本；同商品的重复捕获仍只计一次。不同字节/相近图片也不自动证明是独立实卡。
  已归档的照片复用事实不能因来源滑出90日窗口、current切换或任务主体登记差异而自动消失。同一source的任一已绑定历史捕获均保留复用事实，重新拍照不自动解除；当前价格证据pending或被身份/品相门槛拒绝也仍核对历史照片。历史/其他公开任务的照片仅在原观察及字节绑定核验后用于排除，不能把其金额、日期、身份或样本计数加入当前报告；无法读取的相关证据保留独立性待确认。已核实的复用来源须一并撤销现存派生价格及其受影响历史报告，覆盖原owner，完整审计并可回退，不造源事实冲突标记。

### 完成门槛（所有项均须有实际证据）

1. 原始失败样本与对照回归通过，证明旧结构兼容且真实事实篡改仍被拦截，串码不再充当卡号；污染派生数据修复前后及回退有记录。
2. 预先固定至少10位真实高流通球员作为验收组，必须包含库里、詹姆斯、文班亚马；审计报告披露完整名单及所有失败，不按结果挑选。至少8位有可核验同款成交，至少5位形成有效卡款趋势及球员层面行情；在至少3个不同的完整历史报告日回放达标。此门槛是上线最低门槛，不替代对全部球员的正确处理和覆盖提升。
3. 人工核验至少30笔实际纳入成交，覆盖热门球员、裸卡/评级、常见平行及历史窗口；正式身份无已知误并，证据不确定者退出统计。报告实际核图/核版本范围与未覆盖风险。
4. 历史补采跨多轮实际推进，新成交增量更新与同日重跑幂等经云端验证；至少两次独立云端后台更新完成且能看到新鲜度与历史覆盖，不用一次手动计算冒充持续日更。
5. 网页、API及个人iPhone开发签名手机端实际发布；真实鉴权路径、搜索/排序/展开来源/单球员刷新、账户隔离及真机版本/启动均验证。保留生产成本worker开启及DeepSeek/独立搜索配置，备份/回退可执行。
6. 未运行测试、缺样本、真机未连接及其他阻断项如实保留为未完成；上述业务门槛未达成不得标记任务完成。
