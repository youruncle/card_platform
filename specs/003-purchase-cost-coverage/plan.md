# 实施计划

1. 检查现有 search-plan → 已绑定账号 search → search-result → 账本/审计 → 列表/详情链路，读取当前账户覆盖基线。
2. 使用已有加密账号和密钥执行真实查询；按完全相同关键词组合复用本轮响应，逐卡重查所有权和身份、执行原有 resolve_search。已有人工账本不刷新，仅刷新已有卡淘来源成本；无成本者正常确认。遇登录、验证码或限流停止，连续失败停止，保留逐卡结果。
3. 只修改成本金额展示：提取小组件统一处理 null 与真实零值，列表/详情未知时隐藏成本金额区域，保留查询/手动编辑入口及错误提示。
4. 组件红绿测试与已有成本查询/账户/匹配回归，检查 TypeScript；真实数据覆盖单独记录，不把模拟测试称为真实验收。

无需迁移或修改估值；沿用 Python Decimal、numeric 和订单来源审计。当前独立 worktree 初始干净。此处为唯一 spec/plan/tasks。

## 实测定位后的调整

216 个候选的 cProfile 显示约 72.6 秒中 63.6 秒用于重复产品名称变体计算。为完成批量查询，对产品名称字符串的不可变变体增加最多 4096 项 LRU 缓存；不缓存订单、账户或匹配决定，不改变匹配门槛。相同样本剖析约 8.5 秒。共享纯函数变更需完整后端回归。

实时查询性能：candidates 增加可选 order_scope，在 SQL 中限定 owner 与本次订单。resolve_search、图片补证和自动确认均传递该范围，既有事后 fresh_ids 过滤保留；离线/人工确认默认仍检查全部订单。避免全库历史候选增长导致逐卡查询耗时累积。PostgreSQL 红绿测试验证无关旧单不会进入实时评分。
