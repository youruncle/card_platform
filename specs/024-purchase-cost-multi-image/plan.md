# 024 实施计划

**Goal:** 补强现有成本证据链并如实评估其他无成本卡。
**Architecture:** 保留订单解析、身份评分、分配与提交职责；新增购买商品专用多图观察模块，不改变估值图片验证器的规则。使用现有公开商品解析器绑定图组，观察与保守策略分别测试。
**Tech Stack:** Python/FastAPI、Pydantic、httpx、现有 PostgreSQL 服务与 pytest。
**Spec:** spec.md；上游方案 ../023-purchase-cost-audit/improvement-proposal.md。

## 约束
本地实现，无真实写入或部署；私有证据存 .runtime；沿用工作区；同一份 tasks.md。已授权方案自主执行，使用 systematic-debugging、TDD、executing-plans、verification-before-completion。

## 文件与顺序
1. 受限 freeze.py 冻结样本、代码和证据哈希，完整知识库构建一次 resolver 做基线。所有业务修改等待基线完成。
2. purchase_cost_images.py：图组来源、受限读取、结构化视觉观察、证据绑定、保守字段策略；test_purchase_cost_images.py 先失败再实现。复用 ingestion/cardhobby_public_item.py，公开价格丢弃。
3. purchase_cost_service.py / purchase_cost_inference.py 集成专用多图证据，不放宽旧门槛；精确绑定、失败字段门、历史缓存隔离。
4. purchase_cost_search.py / 身份局部逻辑：修复可复现多人与占位符/简称问题，已有实现无需重复。
5. 复现 sync 幂等修复，评估已有行为，补遗漏诊断；测试保留既有分配、财务阻断。
6. 同一私有样本回放、开发反例与全套 API 测试，生成公开聚合报告及私有逐卡结果。

## 审核重点
URL 重定向与跨商品图片；贴纸与发行量误充限编；同版不同平行/多实物；旧不同缓存；状态过期和到付缺口。每项纳入相关测试与结果报告。

## 2026-10-19：历史资料库执行计划

**Goal:** 完整下载可访问购买历史及多图，复用商品文字/观察，支持分段本地匹配，完整验证100例。
**执行:** 用户已明确批准四步并要求开始；原生独立工作区实施，同份Spec Kit记录，按测试先红后绿执行。

### 接口与顺序
1. `CardHobbySession.read_history_page(cursor=None)`：固定全日期/全部状态范围，读取单页及详情，返回orders/next_cursor；`CardHobbyAccountService.history_page`复用现有登录与账号锁，返回不含凭据的账号绑定键。先测试分页/详情失败、跨查询跳转和账号切换。
2. `purchase_cost_archive.py`：私有按owner分区的原子文件资料库，保存订单快照、checkpoint、受限原图和商品独立文字；图片哈希校验、账号隔离、完整性/新鲜度判定。新增`purchase_cost_catalog.py`进行独立商品多图读字、保存原文和字段；文字仅用于检索，不冒充成对版本证据。测试中断恢复、损坏、改图及未知字段。
3. `purchase_cost_history.py`及`purchase_cost_api.py`：按页同步与有界商品准备/比对接口，调用既有sync/resolve/confirm；持久化快照不是已分配成本；使用当前owner和完整覆盖范围。提供可续跑CLI用于本次100例，不开放跨用户标识。
4. `purchase_cost_images.py`和`purchase_cost_service.py`：私有图缓存用于真实观察；按当前完整绑定保存每候选观察；每步至多核验2个，跨步完成整个竞争域。保存same但场域不完整时保持总闸。格式/别名非关键差异归一化，保留真正版本冲突；不增加未经校准的分数写账出口。
5. 本地针对性与隔离数据库测试、真实100例全量回放/正常服务写账核验；已知负例全部审计。当前生产源码为发布基线，只叠加本轮补丁，检查worker及健康，不覆盖其他未验证修改。

### Review Focus
- 中断/分页漂移：不标完整，允许重启全扫且幂等保存。
- 原图改动/账号切换：旧图片/字段/成对观察失效。
- 一候选完成而另一失败：保存进度，但没有唯一性授权。
- 卡号/限编/平行真实差异：不得被文字相似度或别名吞掉。
- 多笔同款/已分配/财务缺口：沿用既有选择与原子占用，真实回归对照。

### 真实全量性能诊断后的增量

793 条完整资料下，真实 A018 的重复纯评分成为多轮比对瓶颈。沿用 `purchase_cost_knowledge_scope`，仅在当前 asyncio 任务、当前知识对象和当前操作中缓存纯评分；完整输入指纹、深拷贝和 4096 条 LRU 上限防止变化、调用方修改及内存无界增长。异常不缓存；最终财务、分配与唯一性仍实时执行。先红后绿测试覆盖输入/版本/任务变化和商品文字不能单独授权成本，再以冻结真实输入比较逐项输出哈希及实际耗时。

真实 A001 的 `candidates()` 两轮剖析进一步定位首次评分反复执行相同卡片身份归一化及人物别名构造。`purchase_cost.py` 的 recall/score 复用深拷贝身份，`purchase_cost_bundle.py` 保留原别名计算并按人物与 discovery 模式复用；共享原操作缓存的版本绑定、任务隔离和 4096 上限。范围只含纯计算，不缓存任何动态财务或占用结论。

### 真实完整匹配中的候选范围修复

前六例暴露出按整单记住待核验范围会将同单无关行误当作前候选。范围升级为版本化的 `(order_id,item_id)`，所有未完成、缺图、元数据丢失和消失商品持续保留；订单范围仍用于覆盖及财务检查。旧 order-only 记录无法无损恢复商品范围，显式保留 legacy 范围并阻断授权，不直接清除或改变图片判定。先复现无关行误阻及已删除前候选导致错误写账，再补精确范围、旧新混合记录回归；发布后保存旧部分结果，保持原始账本基线，重跑同100例。

真实多轮中打包模型失败也被重复请求。沿用当前 task/resolver/操作作用域，单独保存有界尝试集合，键含当前完整身份和图片哈希、订单行与摘要、模型及知识版本；先查有效数据库结论，再在外部调用前登记。尝试记录不保存模型结论、不清除总闸，操作退出释放，图片变化及子任务可独立重试。该控制增量不改变匹配政策，已完成案例保留，从当前成对观察检查点接续。

真实 A009/A010 的2/4条原始模型same观察被其他未知候选统一降为uncertain，影响既有待选分支。保留完整逐候选same与同事务未完成总闸；待选仍需通过完整候选规则，默认查询、自动确认及旧worker继续受闸限制，只有既有显式人工选择可写入一件。补两轮、单/多正例及缺图/排队/未确认回归，不改变图片判断规则。按最终政策重跑同100，原基线与此前阶段结果保留。

### 长批次原生进程的内存边界

真实 history10 连续完成18例后，匹配容器触及900MiB限制并被内核OOM终止（exit137），生产API和worker仍正常。CLI增加每进程新完成案例预算；只在逐卡全部轮次及检查点提交后退出，不截断该卡候选范围。唯一父驱动以原生已发布镜像逐卡启动新容器，保留卡内操作缓存，跨卡释放进程内存，仍限制900MiB并记录进程RSS峰值。原100清单、已有18例、成对观察与原账本基线不重置；未完成100时不生成全量完成摘要，并清理旧完成文件。先以真实PostgreSQL验证预算/恢复/原交易和最终汇总，再观察A019独立进程的真实内存与完成情况；若单卡仍越限，再依证据定位其峰值来源。
