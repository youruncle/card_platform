# 技术计划

沿用 FastAPI/asyncio 和现有 Next.js 界面。共享本地 Vision 子进程执行器限制每事件循环两条进程，超时/取消清理整个进程组。方向与 OCR 在同版超时后停止重复等待。裁图独立处理并保持原序，完成后短事务锁定会话、计算版本、写入结果。

正反面识别以可信 OCR 锚点为门控输入，并发执行视觉提取与限编补读；异常时取消关联任务。目录核验与参考图查询并发，参考图设总预算；来源网页抓取复用请求级缓存，维持身份与 URL 校验。扫描进度通过现有 status 接口返回处理数量，前端持续轮询。

验证：先用真实子进程和受控阶段阻塞复现，再验证并发顺序、取消清理、字段证据、锁时机与正常/失败路径；可用现场图片做独立回放，不写入真实卡库。

第二阶段沿用同一规格：共享Vision执行器增加按事件循环维护的故障冷却与单探测恢复，普通OCR/限编/方向均使用该状态。ScannerRecognitionWorker先短连接读取任务，再并发准备两面并发布方向数据，释放连接后执行识别，最后短事务导入。各阶段采用monotonic耗时，SQL状态时刻采用clock_timestamp。图片CPU操作用asyncio.to_thread并保持现有裁切算法与参数。联网与pair结果中追加耗时trace，不修改识别证据或状态门。恢复验证先使用受控真实子进程，再回放原八张图片，禁止写入真实卡库。


发布防竞争：读取任务后保存本次attempt_count/started_at快照，方向与最终发布锁行并核验同次认领、queued/running且尚未入库；失败SQL使用同样条件。删除、新一轮重试及已成功任务的旧结果丢弃。普通OCR以兼容list的执行结果附带status/failure_reason，方向分类器将本地引擎结果附加到流水线计时。

八张回放已定位下一瓶颈为目录LLM联网查询（平均42.49秒），在本次继续保留证据核验。若后续希望先展示视觉结果、后台完成目录，需要设计中间状态、增量结果和统计刷新，不能仅缩短超时导致身份核验静默缺失。
